Incident Response / 3 AM Outage Runbook

Standard emergency procedure for triaging and resolving critical off-hours production outages. Use when woken up by high-severity PagerDuty alerts, major infrastructure failures, or customer-impacting downtime during night shifts.

Step 1: First 5 Minutes (Triage & Verification)

Wake up, confirm the alert is authentic, and claim incident ownership without panic.

3 Checks
#ir-1

Acknowledge Alert in PagerDuty / Opsgenie

Acknowledge the alert within 5 minutes to prevent automatic escalation to secondary on-call and engineering management.

CLI Command / Verification 
# Press ACK on PagerDuty mobile app or respond to phone page
#ir-2

Validate Customer Impact (Is it Real?)

Check live health endpoints, synthetic monitors, and Datadog APM to confirm active degradation vs a false-positive telemetry blip.

CLI Command / Verification 
curl -Iv https://api.yourdomain.com/healthz
#ir-3

Assume Incident Commander (IC) Role

Explicitly declare yourself as Incident Commander in Slack to provide clear leadership and prevent duplicated efforts.

CLI Command / Verification 
# Post in #incident-response: "Taking IC role for alert: Payments API Latency. Investigating now."

#ir-4

Classify Incident Severity (Sev1 vs Sev2)

Sev1: Complete customer outage or revenue halt. Sev2: Significant feature degradation with workaround. Sev3: Minor issue.

CLI Command / Verification 
# If revenue/customers affected > 25% -> SEV-1. Page Engineering VP & SRE leads.

Assign Communications Lead & Update Status Page

Assign a secondary engineer or comms lead to draft internal updates and post initial advisory on status.company.com.

Page Subject Matter Experts (SMEs)

If root cause is outside primary domain (e.g. Postgres DB lock, AWS region outage), page the dedicated secondary database/infra SME.

CLI Command / Verification 
# Use PagerDuty: Escalate to Policy "Database-OnCall" or "Infrastructure-OnCall"
3

Step 3: Rapid Diagnosis & Stop-the-Bleeding

Focus exclusively on restoring customer service. Do not troubleshoot root cause if mitigation is available.

5 Checks
#ir-8

Check Recent Deployments & Infrastructure Changes

90% of outages follow recent code deployments or config changes. Check git log, ArgoCD syncs, and AWS CloudTrail.

CLI Command / Verification 
kubectl get deployments -A -o json | jq -r '.items[] | "\(.metadata.namespace)/\(.metadata.name) \(.metadata.creationTimestamp)"'
#ir-9

Inspect Kubernetes Pod Status & Node Health

Check for OOMKilled pods, CrashLoopBackOffs, eviction storms, or disk pressure across worker nodes.

CLI Command / Verification 
kubectl get pods -A --field-selector=status.phase!=Running
#ir-10

Inspect Database Locks & Active Connections

Check if PostgreSQL/MySQL connection pools are saturated or long-running queries are holding exclusive table locks.

CLI Command / Verification 
SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state FROM pg_stat_activity WHERE state != 'idle' ORDER BY 2 DESC LIMIT 10;
#ir-11

Apply Circuit Breaker or Emergency Rate Limiting

If suffering from traffic surge or DDoS, enable Cloudflare Under Attack mode or adjust ingress rate-limiting rules.

CLI Command / Verification 
kubectl scale deployment/ingress-nginx-controller --replicas=10
#ir-12

Execute Immediate Mitigation (Rollback, Restart, or Failover)

Choose fastest path to restore service: 1) Rollback recent deployment, 2) Restart crashing pods, or 3) Failover DB to replica.

CLI Command / Verification 
kubectl rollout undo deployment/<service-name> || kubectl rollout restart deployment/<service-name>
